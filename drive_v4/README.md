# drive_v4 — 선 추종이 운전하고, 지도는 조언한다

v3는 15개가 넘는 게이트가 모두 통과해야 움직이는 구조라서 출발조차 잘 못 했다. 11/10 실주행 로그를 보면 위치 추정은 대부분 성공했다. 차를 세운 것은 계획기의 곡률·0.2mm 악화 검사와, 정지 중에도 계속 커지는 공분산이었다. v4는 이 구조를 뒤집었다.

## 구조

| 부분 | 역할 | 실패하면 |
|---|---|---|
| 카메라 선 추종 (`drive_v3.local_corridor` 재사용) | 직선에서 운전. 실제 차선 중앙 기준 | 지도로 대신 운전(최근 정합이 있을 때). 둘 다 없으면 0.6초 유지 후 출력 0 |
| 지도 (`drive_v3` 정합 추정기 재사용) | **트랙의 어디쯤인가**만 제공. 차축 위치의 경로 곡률과 진행방향 정렬 | 가중치 w가 줄어들 뿐 정지하지 않음 |
| 융합 | `k = (w·corner)·k_map + (1 − w·corner)·k_local` | — |
| 모터 | 두 바퀴 모두 0.30 이상, 비율 유지. 급코너는 안쪽 바퀴를 0.30과 0 사이에서 시간 평균 | — |

- **지도의 가로 위치는 쓰지 않는다.** live_20261110_182520을 재생해 보면, 직선에서 지도 자세가 실제보다 4~5cm 옆으로 치우쳐 있었다. 그대로 따라가면 반경 17cm로 꺾게 된다. v3의 '3cm 침범' 판정도 같은 원인이었다.
- **코너는 지도 타이밍으로 돈다.** 카메라는 차축보다 약 12cm 앞에 있어서, 카메라가 코너를 보는 순간 꺾으면 너무 일찍 꺾는다(1번 코드의 안쪽 파고들기). 코너 근처에서는 차축이 코너에 도달할 때 경로 곡률로 꺾는다.
- **정지 중에는 불확실성이 늘지 않는다.** 공분산은 이동거리·회전량에 비례해서만 커진다.
- **출발 정합 실패는 정지 사유가 아니다.** 경로를 따라 ±32cm 범위에서 재정합을 시도한다. 그동안은 카메라로 운전한다.
- **트랙 밖에서는 움직이지 않는다.** 11/10 dry 시험에서 차가 사람·책상을 보고 있을 때 경로 재정합이 잡동사니에 맞은 적이 있다. 그래서 차선은 3프레임(약 0.15초) 연속으로 보여야 인정한다. 재정합은 차선이 보일 때만, 지도 단독 주행은 차선을 본 지 1.5초 이내일 때만 허용한다.

## 종료 조건

**stop 인터럽트뿐이다.** Ctrl+C, SIGTERM, SSH 끊김, 차량 버튼 중 하나로 끝난다. 한 바퀴 완료, 계획 실패, 정합 실패로는 끝나지 않는다. 도로가 안 보이면 출력만 0으로 두고 계속 관측하며, 다시 보이면 자동으로 재개한다. 루프가 멈추면 0.5초 watchdog이 모터를 0으로 만든다.

## 실행 (Pi)

```bash
cd ~/drive_v4_trial
venv=~/field_validation_20261110/venv/bin/python
$venv -m drive_v4.run_pi              # dry: 카메라와 판단만, 모터 없음
$venv -m drive_v4.run_pi --drive      # 실제 주행 (Ctrl+C 또는 버튼으로 정지)
$venv -m drive_v4.run_pi --drive --cruise 0.34 --direction ccw
```

기록은 `drive_v4/runs/live_*/steps.jsonl`과 원본 프레임 jpg로 남는다. 출발 자세의 기본값은 오른쪽 빨간선 출발 구역이며, `--pose x y yaw`로 바꿀 수 있다.

## 검증 범위

- `python -m drive_v4.tests.test_core`: 데드밴드, 비율 유지, 급코너 디더링, 정지 중 공분산, 가로 치우침 무시, 검은 화면에서 0 출력.
- `python -m drive_v4.replay RUN...`: 저장된 실주행 프레임을 재생한다. 실제 모터 출력을 그대로 넣고 v4 판단을 비교한다. 182520, 185902, 183231 세 주행에서 v3가 멈춘 구간을 포함해 모든 프레임에서 출력을 낸다. 185902에서 실제 차가 직진해 들어간 코너에서는 v4가 좌회전(k −0.03 → −0.084)을 지시한다.
- **재생은 폐루프가 아니다.** v4의 명령이 실제로 차를 어떻게 움직이는지는 실차 시험으로만 확인할 수 있다. `cm_s_per_duty`, `yaw_gain`, 디더링의 실제 효과는 아직 보정되지 않았다.
- 표지판·미션(STOP, 신호, 교차로 방향)은 아직 연결되지 않았다. 외곽 한 방향 주행만 다룬다.

## 코너 개선 (2026-11-10 저녁)

실주행 195808 로그로 보면 실제 회전량은 명령의 약 0.6배였다(코너 1 0.58, 코너 2 0.60). 4륜 스키드 조향이 회전 중 옆으로 미끄러지기 때문이다. 이 값으로 시뮬레이터를 맞추면 "늦게 잡고 급회전하다 살짝 이탈"하는 실차 양상이 재현된다.

| 변경 | 내용 |
|---|---|
| 회전 모델 | `yaw_gain 0.6`. 같은 곡률을 내기 위해 좌우 차이를 1/0.6배로 준다 |
| 진입 시점 | 차축 앞 2~14cm 구간의 경로 곡률 평균으로 미리 꺾는다 |
| 코너 속도 | 코너에서 바깥 바퀴 상한을 0.6에서 0.5로 낮춘다 |
| 오차 흡수 | 직선에서 (지도 가로 위치 − 카메라 가로 위치)를 학습한다(±5cm 제한). 코너에서는 보정된 지도 가로 위치로 피드백한다 |
| 이탈 방지 | 0.4초 앞 차체 여유가 2cm 안으로 **줄어들 때만** 반대쪽으로 곡률을 더한다(최대 0.03). 정지하지 않는다 |

시뮬레이션(`python -m drive_v4.sim`, 회전 효율 0.6) 결과, 선을 3cm 넘게 침범한 프레임 수는 다음과 같다.

| 조건 | 이전 | 이후 |
|---|---|---|
| 카메라 오차 +5%·+1.5cm | 342프레임, 최대 −5.2cm | 0프레임, 최대 −0.8cm |
| 이상적 카메라 | 327프레임, 최대 −5.3cm | 0프레임, 최대 −1.9cm |
| 카메라 오차 −3%·−1.5cm | — | 0프레임, 최대 −3.0cm |
| 잘못된 출발 위치(이상적·오차) | — | 둘 다 완주, 최대 −2.2cm |

채택하지 않은 것: 최소 곡률 경로(이 차폭으로는 코너에서 가로 여유가 ±1~2cm뿐이라 오히려 반경이 줄었다), 진입 시점 4~22cm(악화), 세 가지를 모두 강하게 적용한 조합(도로 이탈). 시뮬레이션은 실차보다 이상적이다.

## 좌우 회전 효율과 온라인 학습 (v2 출력 보상 이식)

v2 `feedback_driver.Feedback`의 출력 보상을 옮겼다(`TurnGainLearner`). 좌회전과 우회전 효율을 따로 둔다. 시작값은 v2 11/06 실주행 학습값(좌 약 0.63, 우 0.62)이며, 11/10 v4 측정값(좌 0.58~0.60)과 일치한다. 같은 회전 방향이 이어지는 동안 "신뢰도 높은 연속 지도 정합에서 본 회전량 ÷ 적용 PWM의 이상 회전량"을 모아 그 방향 계수를 갱신한다. v2의 안전장치를 유지한다: 좌우 근거 섞지 않기, 10° 이상 회전한 창, 1회 변화 ±0.04, 범위 0.5~1.0. 재정합 순간이나 신뢰도가 낮을 때는 학습하지 않는다.

시뮬레이션(카메라 오차 +5%·+1.5cm):

| 실제 효율 | 학습 | 결과 | 최악 여유 | 3cm 넘게 넘은 프레임 | 끝난 계수 |
|---|---|---|---|---|---|
| 0.60 | 켬 | 완주 | −1.6cm | 0 | 0.62 |
| 0.50 | 끔(0.63 고정) | 완주 | −4.5cm | 76 | 0.63 |
| 0.50 | 켬 | 완주 | **−0.3cm** | 0 | 0.50 |
| 0.60→0.45 서서히 감소 | 켬 | 완주 | −0.2cm | 0 | 0.52(하한 0.5에 걸림) |
| 잘못된 출발 위치 | 켬 | 완주 | −1.5cm | 0 | 0.67(오정합 구간에서 잘못 학습) |

한계: 지도 정합이 엉뚱한 곳에 맞은 동안은 잘못 학습할 수 있다(위 0.67). 갱신 폭 제한 덕분에 완주에는 지장이 없었다. 하한 0.5보다 실제 효율이 낮으면 따라가지 못한다.
